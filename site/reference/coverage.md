# Coverage

"Everything" means everything the configured credentials are authorized to observe through supported GitHub
sources. GitHub has no globally complete activity feed, and this service does not pretend to have one. This page says
what is captured, what each source needs, and what cannot be seen or reconstructed.

GitHub facts below were checked against docs.github.com and the GitHub changelog on 2026-10-27. Where GitHub's
documentation is ambiguous, this page says so.

## Sources at a glance

| Source | Subjects | Credential | Real-time | Recoverable after downtime | Authoritative |
|---|---|---|---|---|---|
| GitHub App webhooks | `…webhook.<event>.<action>` | App installation (webhook secret) | yes | only by manual redelivery (see below) | yes |
| Notifications | `…notifications.thread.observed\|updated` | classic PAT, `notifications` or `repo` scope | polling, ≥ 60 s by default | changed threads still listed by `/notifications` | notification state only |
| Events API | `…activity.<event>.observed` | PAT, or installation for org/repo feeds | 30 s to 6 h latency (GitHub) | last 300 events / 30 days | yes, but bounded |
| Org audit log (optional) | `…audit.<category>.<action>` | org owner's classic PAT, `read:audit_log`; **Enterprise Cloud only** | polling | within GitHub's audit retention | yes |
| Installation reconciliation | `…reconcile.installation*.…` | App JWT + installation token | hourly by default | current state | current state; changes are inferred |
| Snapshots / backfill | `…reconcile.<kind>.snapshot\|changed` | installation token | interval (6 h default) | current state of resources updated in the window | current state, **not** history |
| Enrichment (optional) | `…enrichment.<kind>.fetched` | the account's PAT | budgeted | — | current state at fetch time |
| Collector meta | `…collector.coverage.gap_detected`, `…collector.access.lost\|restored` | — | — | — | generated by this service |

## GitHub App webhooks (primary)

An App installation receives the events it is subscribed to, for the repositories it can access (all, or a
selection) on the account it is installed on. A personal-account installation covers that user's repositories, not
repositories the user merely contributes to.

| Category | Webhook events | App permission (read) |
|---|---|---|
| Issues and comments | `issues`, `issue_comment`, `milestone`, `label` | Issues |
| Pull requests, reviews, review comments, threads | `pull_request`, `pull_request_review`, `pull_request_review_comment`, `pull_request_review_thread` | Pull requests |
| Pushes, refs, branches, tags | `push`, `create`, `delete` | Contents |
| Commit comments | `commit_comment` | Contents |
| Releases | `release` | Contents |
| Forks | `fork` | Contents |
| Stars, watches, repository metadata | `star`, `watch`, `repository`, `public` | Metadata |
| Discussions | `discussion`, `discussion_comment` | Discussions |
| Workflows | `workflow_run`, `workflow_job` | Actions |
| Checks | `check_run`, `check_suite` | Checks (write needed only for `requested`/`rerequested` actions) |
| Deployments | `deployment`, `deployment_status` | Deployments |
| Members, teams, organization | `member`, `membership`, `team`, `team_add`, `organization` | Organization: Members (and repository Administration for `member`) |
| Installation lifecycle | `installation`, `installation_repositories`, `installation_target` | none; always delivered |
| Anything else | any event the App subscribes to | per event |

**Unknown events and actions** are stored and published unchanged. The subject tokens are encoded deterministically
(see the [event contract](/reference/event-contract#token-encoding)), so a new GitHub event type needs no release.

Limits documented by GitHub:

- Payloads larger than 25 MB are **not delivered** at all.
- `push` lists at most 2048 commits. No `push`, `create` or `delete` events are created when more than 3 tags are
  pushed at once.
- A push payload is not a source-code export. Commits list metadata, not file contents. pulse-github never clones
  repositories or downloads artifacts.
- GitHub expects a 2xx within 10 seconds. pulse-github answers right after the durable commit (milliseconds).

### Delivery recovery

GitHub does **not** automatically redeliver failed webhook deliveries. When the receiver was down, unreachable, or
answered 503 (storage pressure):

1. Find the failed deliveries in the App's **Advanced → Recent Deliveries**, or through the API (`GET
   /app/hook/deliveries`, with the App JWT), and redeliver them (`POST /app/hook/deliveries/{id}/attempts`). The UI
   shows deliveries from the past **3 days**. The API documentation does not state a retention period, and this
   service has not verified one.
2. A redelivery keeps the original `X-GitHub-Delivery`. pulse-github deduplicates it, so redelivering something that
   was already stored is harmless.
3. Older losses are **irrecoverable as webhook events**. Reconciliation and backfill show the current state of what
   changed. The Events API may show some of the activity if it is still within its 300-event, 30-day window.

pulse-github does not call the redelivery API on its own, because that is a GitHub mutation. Automating it is a
possible future extension.

## Notifications

- **Endpoint:** `GET /notifications?all=true` for the authenticated user.
- **Token:** a **classic personal access token** with the `notifications` or `repo` scope. GitHub supports no other
  token type here: fine-grained PATs, App installation tokens and App user tokens do not work. `doctor` and the
  poller check `GET /user`. The token must report OAuth scopes (fine-grained tokens report none) and belong to the
  configured account. The ID is pinned on first use.
- **Coverage:** threads in any repository the user receives notifications for, including repositories the user does
  not own. Each observation is the **notification thread state**: reason, unread, `updated_at`, `last_read_at`,
  subject title/type/URL and repository. It is not the underlying issue, comment or review, which may be
  invisible to every other source.
- **Change detection:** a fingerprint over reason, unread, `updated_at`, `last_read_at`, subject title, type, URL and
  latest comment URL. The first observation is `thread.observed`; later changes are `thread.updated`.
- **Polling:**
  - `since` = newest `updated_at` seen minus `overlap` (10 min). The first poll reads the last `initial_lookback`
    (7 days).
  - `If-Modified-Since` with GitHub's `Last-Modified`.
  - `X-Poll-Interval` is honoured.
  - `per_page=50` is GitHub's maximum.
  - `max_pages` bounds each run. When more threads changed than fit, the newest are read, the cursor moves on, and
    one `collector.coverage.gap_detected` event names the unread window.
  - Read-state changes do not move `updated_at`, so a periodic **full sweep** without `since` (default every 6 h)
    catches them. It is bounded by `max_pages` too: older threads beyond the budget are not re-checked, and the sweep
    reports that once as a gap.
- **Never mutated:** nothing is marked read, subscribed or unsubscribed.
- **Not visible:** notifications GitHub no longer lists; threads that changed more often than one poll interval (only
  the latest state is seen); notification content beyond the subject.

## Events API (supplementary)

- **Feeds:**
  - `/users/{u}/events`: includes private events when authenticated as that user.
  - `/users/{u}/received_events`.
  - `/users/{u}/events/orgs/{org}`: needs authentication as that user.
  - `/orgs/{org}/events`.
  - `/repos/{o}/{r}/events`.
- **Bounds (GitHub):**
  - At most **300 events**, only from the last **30 days** (reduced from 90 days on 2025-01-30).
  - Latency from **30 s to 6 h**.
  - `per_page` up to 100.
- **Payloads:** since 2025-10-07, `PushEvent` carries no commit list, size or `distinct_size`, and `author_association`
  was removed from PR, review, issue and comment events. Push events are tagged with the qualifier
  `push_without_commit_list`.
- **Not an audit trail:** visibility depends on the endpoint and token, and private interactions may be missing.
- **Gap detection:** each poll pages until it reaches the newest event ID already stored. If that event is no longer
  reachable (more than 300 newer events, older than 30 days, or the page budget ran out), a
  `collector.coverage.gap_detected` event is published with the time window. After downtime longer than 30 days the
  gap kind is `outside_retention`.

## Organization audit log (optional)

`GET /orgs/{org}/audit-log`:

- **Availability:** only for organizations on **GitHub Enterprise Cloud**. Needs an organization owner's classic PAT
  with `read:audit_log`. It is not available to installation tokens.
- **Retention:** GitHub's documentation gives differing figures (180 days, "up to seven months", Git events 7 days).
  Treat retention as limited and unverified.
- **Reading:** ascending order (`order=asc`) with a `created:>=` phrase and a 1-minute overlap, deduplicated by
  `_document_id`. The exact phrase date format and ordering are taken from GitHub's documentation; they were tested
  against a fake server only.

## Reconciliation and backfill

- **Installations:** `GET /app/installations` (App JWT) and `GET /installation/repositories` (installation token)
  keep the stored installations and repository access up to date.
  - Installations missing from the App's own listing are marked removed and emit `collector.access.lost`.
  - Repositories that leave an installation are published as `installation_repository.access_removed`, which means
    **lost access, not deletion**.
- **Resources:** `repository`, `issues` (including PRs as issues), `pulls`, `releases` and `workflow_runs`, for the
  installation's accessible repositories that pass the account's filter. Only resources updated (or created, for
  releases and runs) within the job's window are read. Defaults: reconciliation 24 h lookback every 6 h; backfill
  7 days; an explicit maximum of 366 days.
- **Budgets:** requests per job (300 for reconciliation, 1000 for backfill by default) and wall-clock time per
  reconciliation run. An exhausted budget ends the job with a `request_budget_exhausted` gap. There is no unbounded
  full-history crawl.
- **Resumable:** the cursor (repository list, current kind, next page URL) is stored with every page.
- **Fair:** one request per account per turn.
- **Semantics:** a first sighting is `reconcile.<kind>.snapshot`. A different fingerprint is `reconcile.<kind>.changed`
  with `provenance.inferred = true`. Neither has `occurred_at`. Snapshots are the **current state**: they do not
  reconstruct edits, intermediate states, deleted comments or who did what.
- **Ambiguity:** a 404 or 403 skips the resource and records it in the job. Nothing is ever published as deleted
  because of a 404, because "not found" also means "no longer visible to this credential".
- **Coexistence:** snapshots never suppress or replace webhook events. Both are published, with different sources.

## What cannot be observed or reconstructed

- Activity in repositories or organizations none of the configured credentials can access.
- Webhook deliveries lost while the receiver was down and not redelivered within GitHub's delivery history.
- Payloads larger than 25 MB (GitHub does not send them); pushes of more than 3 tags (no events created).
- Edit histories, intermediate states between two snapshots, deleted content, and exact times of inferred changes.
- Events API entries older than 30 days or beyond the newest 300; commit lists of Events API pushes.
- Personal activity of users who are not configured accounts (routing never infers from actor logins).
- Organization-wide security, billing and admin activity, unless the audit log is available and enabled.
- Anything a credential could see before a permission change but not after it.

## How changes affect coverage

| Change | Effect | Signal |
|---|---|---|
| App permission or subscription removed | Fewer webhook events; snapshot kinds may answer 403 (skipped) | `doctor` warns about missing subscriptions; job notes; `collector.access.lost` for feeds |
| Installation suspended or uninstalled | No webhooks; reconciliation marks it | `webhook.installation.suspend\|deleted`, `reconcile.installation.*`, `collector.access.lost` |
| Repository removed from a selected-repository installation | No webhooks for it | `webhook.installation_repositories.removed` or `reconcile.installation_repository.access_removed` |
| PAT expired, revoked or missing a scope | Notifications/activity stop | `collector.access.lost`, `pulse_github_coverage_degraded`, `credential_failures_total` |
| Service down for less than the overlap | Nothing lost from polling sources | none needed |
| Service down for hours | Webhooks lost unless redelivered; polling recovers within retention | gap events if cursors were lost |
| Service down for more than 30 days | Events API history lost | `outside_retention` gap |
| Storage full | Webhooks answered 503 (GitHub will not retry); pollers pause and catch up after recovery | readiness 503, `webhook_admission_open 0` |
| Account renamed on GitHub | Routing key and subjects stay the same; the payload shows the new login | `installation_target.renamed`, log line |

## Data protection

Private GitHub content (issue bodies, comments, code review text, private repository names) is copied into Pulse,
where Pulse's own access control and retention apply. Grant `subscribe` on `evt.github.>` or `evt.github.<account>.>`
only to clients that may read that content. Losing access on GitHub, or deleting content there, does **not** delete
events already in Pulse. Use Pulse's stream retention, or a purge by an operator, if that is required. pulse-github's
own SQLite keeps raw payloads only for the configured retention: 7 days for inbox bodies and published outbox rows by
default.
